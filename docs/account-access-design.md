# Google and Apple account access

Created by Cory McCabe.

Followthrough owns the account and workspace. The sign-in screen shows **Continue with Google**, **Continue with Apple**, and **Continue with ChatGPT** in one list. People can create an account or return to one with Google or Apple. After sign-in, Followthrough offers calendar and inbox setup for that account. People can skip either step and use the planner with manual task entry. The model that processes an AI feature has its own configuration and plays no part in signing in or choosing a workspace.

## Public launch

Require both primary sign-in methods on the web, iPhone, and Mac. ChatGPT is an optional method. This gives people a choice on every platform and supplies the equivalent privacy-preserving login option Apple calls for when a third-party login is used for the primary account. The Watch continues to follow the iPhone’s account. [App Store Review Guidelines §4.8](https://developer.apple.com/app-store/review/guidelines/)

| Capability | Launch decision |
| --- | --- |
| Google Calendar | Include availability from selected calendars and optional task-block publishing to one eligible Google calendar. Verify the launch OAuth client’s required Calendar scopes and its actual supported destinations. |
| iCloud Calendar | Include availability from selected calendars, using the existing separately authorized iCloud connection. Enable iCloud task-block publishing after the server writer passes live create, update, move, and cleanup checks in dedicated iCloud calendars. Apple-only users can schedule inside Followthrough with iCloud conflicts before external publishing is available. |
| Gmail | Include optional read-only task suggestions per connected inbox only when Google verification and any required restricted-scope security assessment are confirmed for the production integration. Keep the feature off for public users until then. |
| iCloud Mail | Defer direct inbox sync and suggestions. Validate Followthrough’s eligibility for Apple’s separate data authorization, mailbox discovery, and permission and revocation behavior before offering it. |

Email scope is suggestions from recent Inbox conversations and relevant sent replies. Accepted suggestions become tasks. Composing, sending, modifying mail, and indexing whole mailboxes are outside this release. Existing forwarding-based capture is a separate feature. [Gmail API scopes](https://developers.google.com/workspace/gmail/api/auth/scopes) · [Apple iCloud data authorization](https://support.apple.com/en-us/121539) · [Current Gmail review notes](google-verification-submission.md) · [Calendar destination baseline](../native/README.md#calendar-destinations)

## Account and data model

| Record | Design |
| --- | --- |
| Followthrough account | One personal workspace per account, owned by a stable internal ID. Generate an opaque ID for new accounts and retain the existing `owner_id` for migrated accounts. |
| Sign-in identity | Many identities may point to one Followthrough account. Each verified provider issuer and subject pair can point to only one account. Email, including an Apple relay address, is display/contact metadata. |
| Session | A revocable Followthrough session carries the internal owner ID. Resolve ownership on the server before accessing workspace data. Browser cookies and native credentials use their own lifecycles. |
| Connected account | An owner-scoped connection has a provider, verified provider account reference where available, label, and grants for its capabilities. Store provider credentials encrypted on the server. A connection by itself confers no Followthrough sign-in rights. |
| Calendar and inbox preferences | Calendar and inbox references include the connection ID and provider resource ID so resources from two accounts remain distinct. Store availability selection and all-day rules per calendar, one optional workspace publishing destination, and email suggestions and sync state per inbox. |

Google supplies a stable `sub` even if the user’s email changes. Normalize accepted Google issuer values before lookup. Use the verified Apple subject in Followthrough’s configured Apple app group and accept Apple’s relay address or an absent profile field. Collect the name when Apple returns it on first authorization, if available. Apply the same owner model to AI features, including the existing server-side model configuration. A model change cannot grant account access or expand a data grant. [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) · [Apple authentication and user information](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple)

## First visit and returning sign-in

1. Center all three sign-in choices in one column with the same button width. Use the providers’ official **Continue with Google** and **Continue with Apple** controls. The sign-in methods request basic identity. Google uses `openid email`. Apple can return a name and email, with Hide My Email supported.
2. Verify the provider response on the server and look up the provider subject. A recognized identity opens its workspace immediately. An unrecognized Google or Apple identity sees **Create a Followthrough account** or can return to sign in another way. Confirm creation once and start with an empty workspace. If the user cancels or verification fails, return to the sign-in screen with a retry and keep the workspace state intact. A matching address never merges or links accounts.
3. After creation, show **Set up your connections** with separate calendar and inbox actions and **Set up later**. Returning users go directly to the workspace. A connection that needs attention gets a reconnect action in Settings.

Use the same account lookup on all platforms. On web, use Followthrough’s verified Google and Apple callbacks and issue a secure, HTTP-only app session cookie. Associate the Apple web Services ID with the primary app ID. On iPhone and Mac, show the same options in the existing system sign-in sheet. After provider verification, reuse the native one-time code and verifier exchange to issue Followthrough’s device session. Show the selected account before connecting the device. Switching workspaces must keep pending edits and captures associated with their original owner. [Apple web sign-in configuration](https://developer.apple.com/help/account/capabilities/configure-sign-in-with-apple-for-the-web/) · [Apple token verification](https://developer.apple.com/documentation/signinwithapple/verifying-a-user) · [Existing native exchange](../app/api/native/session/route.ts)

Bind every callback to a short-lived, single-use transaction with an explicit purpose, approved redirect, and the initiating session when linking or granting access. Verify issuer, audience, signature, expiration, and the nonce where used. Use authorization code exchange and PKCE where supported, including the native pairing exchange. For Apple’s cross-site callback, save the verified result to the server transaction, then verify the originating app session before committing a link. Rotate app sessions on sign-in. On identity revocation, invalidate sessions established through that identity and keep other active sign-in methods available. [Google token verification](https://developers.google.com/identity/openid-connect/openid-connect) · [Apple token verification](https://developer.apple.com/documentation/signinwithapple/verifying-a-user)

## Consent and initial connections

Offer the signed-in provider first. Before requesting data, tell people which account will be connected, what Followthrough will do, and that they can skip. Require a separate action and successful provider authorization for each capability. For a Google data grant, include `openid` alongside the data scopes and verify the returned account subject. Compare it to the signed-in Google subject for the first suggested connection. If Google returns a different account, offer to add it explicitly or let the user switch back. Keep the Followthrough session on its original workspace. [Google sign-in best practices](https://developers.google.com/identity/siwg/best-practices)

| Action | Permission and default behavior |
| --- | --- |
| **Connect Google Calendar** | Request `calendar.calendarlist.readonly` and `calendar.events.freebusy`. Show the actual account and suggest its primary calendar for availability. Start reading busy times after the user confirms their selection. Leave other calendars unselected until added. |
| **Publish task blocks** | Leave publishing off until the user chooses a destination. Prefer a dedicated Followthrough calendar when supported using `calendar.app.created`. If the user chooses a supported owned calendar, request `calendar.events.owned` as needed. Manage only Followthrough’s marked events. A destination is also checked for conflicts and the scheduler ignores its own task blocks. |
| **Connect iCloud Calendar** | Ask for the Apple Account address and an app-specific password through the existing CalDAV setup. If Apple supplies a non-relay address at sign-in, offer it as an editable hint. For a relay address, leave the field blank. Confirm the discovered account and ask the user which calendars should block scheduling. Server use of this credential is limited to iCloud Calendar. |
| **Enable Gmail suggestions** | Ask for `gmail.readonly` independently of Calendar, and verify the authorized mailbox before enabling it. Explain the recent Inbox and sent-reply reads and disclose any AI processing for this feature before the user opts in. Start review only for the confirmed inbox. |
| **Connect iCloud Mail** | Omit the connect action until supported. The Apple identity and CalDAV setup supply no Mail consent. Users may independently connect a supported Gmail inbox or continue with manual task entry. |

The app tracks which permissions were actually granted. A denial, cancellation, missing mailbox, or organization restriction affects only that capability. Confirm the server has working credentials before enabling background sync. Keep scheduling inside the app available with zero connections. Use the minimum scopes needed, keep provider credentials out of client responses and logs, and stop background reads when consent is withdrawn. Limit Gmail data sent to a processor to the user-authorized suggestions feature, with no general model training and no automatic transfer to a newly configured model provider. [Google Calendar scopes](https://developers.google.com/workspace/calendar/api/auth) · [Google granular permissions](https://developers.google.com/identity/protocols/oauth2/resources/granular-permissions) · [Google Workspace user data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) · [Apple app-specific passwords](https://support.apple.com/en-us/102654)

## Settings

- **Account → Sign-in methods.** Show connected login methods and **Add sign-in method**. Require recent proof of an existing sign-in and proof of the newly selected provider identity before linking. If the identity already belongs to another workspace, keep both intact and direct the user to sign in to the original workspace. To remove a method, confirm another usable sign-in remains. If the only provider is lost, direct the user to that provider’s account recovery. Offer device sign-out and in-app account deletion as distinct actions. Deletion revokes sessions, provider grants and Apple sign-in tokens, and deletes workspace data with explicit confirmation. [Apple account deletion guidance](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)
- **Connected accounts → Add account.** Choose Google or Apple, then Calendar or a supported inbox. Allow more than one account of either provider. A provider account already connected to this workspace opens its settings so the user can add a capability or reconnect. A different account creates a separate row after confirmation. Each row shows its account label and the status of each capability. Any Gmail connection is independent of whether the account has Google Calendar enabled.
- **Calendars that block your tasks.** Group calendars by connected account. Choose individual calendars and their all-day rules. In **Task calendar**, select one eligible destination or **Off**. Adding an account never changes an existing destination. Before moving a destination, show the old and new calendars and reconcile only Followthrough-created events. If a destination is removed or access is lost, pause publishing until the user chooses a destination or turns publishing off.
- **Inboxes.** Show each authorized mailbox with a separate **Suggest tasks** toggle, account name, and reconnect or remove action. The sign-in account is suggested first during setup. Every enabled inbox contributes to the Suggestions queue with its source identified. Turning off an inbox stops its scans and clears its pending suggestions while keeping accepted tasks. The same controls can cover additional iCloud inboxes once Mail is supported.
- **Disconnect or reconnect.** Disconnecting a data connection stops its jobs and removes its credentials and derived connection state. If Calendar and Gmail share a Google grant, let the user turn off one feature locally or remove the whole grant with its full impact shown. For an iCloud app-specific password, remove the stored credential and show the user how to revoke it at Apple. Losing an authorization marks the affected connection as **Reconnect**. Reconnect verifies the original account before resuming. If an availability source fails, retain the last plan and pause publishing until the user reconnects or explicitly removes that source. Sign-in and task data remain available. [Google grant revocation](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke) · [Apple password revocation](https://support.apple.com/en-us/102654)

## Existing workspaces and rollout

The current web auth helper reads Sites-injected ChatGPT identity, and native authorization derives its owner from that same helper. D1 rows and native sessions are keyed by that owner, and calendar credential encryption includes it. The repository already models multiple Google calendar accounts and per-account Gmail review. The iCloud model currently has one credential and one set of selections, so multiple iCloud accounts require extending that model and updating sync to resolve the owning connection. Existing settings can provide the calendar and inbox controls above. [Web auth](../app/chatgpt-auth.ts) · [Owner checks](../lib/http.ts) · [Native authorization](../app/api/native/authorize/route.ts) · [D1 schema](../db/schema.ts) · [Calendar credentials](../lib/calendar-security.ts) · [Connection model](../lib/calendar-model.ts) · [Gmail review state](../lib/suggestion-store.ts) · [Calendar settings](../components/calendar-settings.tsx)

1. Prove the canonical sign-in and callback URLs can run without the Sites ChatGPT access gate while private routes require a Followthrough session. If the current host cannot support that boundary, use an app-controlled entry point with supported access to the workspace store or a rehearsed data migration. Preserve the purpose-specific authentication of native APIs, shortcuts, calendar actions, and inbound email. [Current routing and deployment](domain-migration.md)
2. Let an existing user choose ChatGPT and open **Sign-in methods** to add Google or Apple. Verify the current workspace session and the new identity, then attach the identity to the same owner ID. Keep tasks, revisions, calendar and inbox choices, working grants, device credentials, and signed integrations under that owner. Preserve older connection references until the user reauthorizes and the provider account can be verified. Keep ChatGPT available as an optional login through a verified Sites identity handoff.
3. Validate both logins on each platform and rehearse cutover and rollback on sample workspaces. Confirm which Calendar scopes and destinations the production integration can offer. Exercise migration with an existing workspace and pending native edits. Gate Gmail and iCloud publishing independently using the conditions in the launch table. [Google verification record](google-verification-submission.md) · [Restricted-scope assessment handoff](google-security-assessment-handoff.md)

## Acceptance scenarios

| Task checklist | What implementation must demonstrate |
| --- | --- |
| Account model without ChatGPT | A new user can sign in, create a task, and return with no ChatGPT account or data grants. Linking a second login opens the same owner. Two workspaces with matching display email remain isolated. |
| Google and Apple sign-in and creation | Both providers support new and returning users on web, iPhone, and Mac. Apple Hide My Email and a returning response with no name work. Canceled, expired, replayed, or wrong-audience callbacks do not create, link, or switch an account. |
| Consent, permissions, and defaults | Sign in with Google A, connect only its Calendar, and use the planner with Gmail off. Selecting Google B at consent requires explicit confirmation and never switches the workspace. Sign in with Apple and Hide My Email, then connect iCloud Calendar with separate credentials or skip setup. Publishing requires an explicit destination. |
| Multiple accounts, calendars, and inboxes | Connect two Google and two iCloud calendar accounts and choose individual conflict calendars. Enable two eligible Gmail inboxes, turn one off, and verify the other keeps working. Remove the current publishing connection and verify that no other calendar receives writes. |
| Launch providers and capability limits | Google and Apple pass in the intended production routing. ChatGPT is visible beside them. Verify Calendar permissions and destination controls, then test with Gmail and iCloud publishing disabled. iCloud Mail is omitted, manual task entry still works, and migrated users can return without ChatGPT. |
