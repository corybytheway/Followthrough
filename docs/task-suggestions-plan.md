# Task suggestions

Author: Cory McCabe

## Experience

One collapsed-by-default “Suggested tasks” section between capture and today’s tasks, shared across web, Mac, and iPhone. Remember expansion on each device. Compact cards lead with a project-colored dot, project name, and a contextual action title. All three clients retain the bold “Based on:” label, then Task history for the quoted source task name, or Gmail (with its official logo) and the quoted email subject. The complete source flows across the card’s full inner width, including the space below the checkmark and X; wrapped lines use that same width. Omit the explanation and separator dot from the source line. The next line retains compact duration (“10m task”) and priority, separated by a visible dot. Today has no Gmail check timestamp or refresh control.

Show every related outcome as its own task row, adjacent to its linked tasks, with a subtle link connector and dependency order. Acceptance preserves the group and its blockers; never substitute “+1 related task” for the actual task title. Keep feedback (“Was this a good suggestion?” or “Were these good suggestions?”) separate from the checkmark acceptance control and X dismissal control. Positive feedback does not dismiss a suggestion.

The checkmark immediately accepts the proposed fields and invokes the existing scheduler on every client, without opening a review dialog. Linked tasks are accepted together. Edit accepted tasks through the normal task editor afterward. X dismisses the suggestion or linked group. Thumbs up/down open short “Suggest more/less like this?” confirmations naming the pattern affected, with right-aligned actions, a gray Cancel button on the left, and mint primary action on the right. The iPhone uses a compact, expandable sheet; accessibility text sizes open a larger sheet. Feedback never accepts a task. It is scoped to the user and pattern, reversible in Settings. Gmail feedback concerns similar actions, never silently filters a sender’s entire mailbox.

## Sources

- Gmail: optional read-only upgrade for the existing Google account, seven-day inbox lookback excluding Promotions, Social, Spam and Trash; recent sent replies in those conversations supply completion context. Suggest only clear actions related to an existing Followthrough project, using its name, aliases, description and email context. Skip uncertain relationships and unrelated personal mail. Every task in a linked group must match an existing project. Validate this during analysis, listing and acceptance, with matching web/native cache filters. When there are no projects, skip mailbox reads and AI requests. Fixed server retrieval, no attachments or model tools. Reuse configured OpenAI with store:false and zero-output support. Separate twenty-request daily allowance; ten conversations per batch; fifteen-minute checks and manual refresh. Preserve checkpoints and unfinished work. Restricted-scope verification and security assessment gate wider release.
- Frequency: infer cadence from at least four separate completions across at least three days, with consistent intervals. Recognize morning/evening windows separately. Confirm the next occurrence; do not automatically schedule a permanent recurrence. Existing active copies suppress candidates.
- Personal workflow: after at least three repeated adjacent completed task pairs within a project, suggest the usual next action after a new matching first action completes. Require at least 75% consistency and no existing active matching task. Use the user’s historical task fields, never invent a workflow.
- Task history: rank ready, currently unblocked tasks using explicit deferrals in the last thirty days (four points each, counting at most six deferrals), weeks without recorded progress (one point each, capped at four), and fortnightly age (one point each, capped at two). Require two deferrals or five days of inactivity (lowered from fourteen for pilot testing). Exclude waiting, future-start, deleted and completed tasks. Age is weak evidence, never proof of avoidance. Record explicit postponements separately from automatic planning. Progress means completed checklist steps or reduced remaining effort and resets earlier deferral evidence. Becoming unblocked or returning from waiting starts a fresh eligibility window. Offer the first unfinished step with enough parent-task context to make sense on its own. Skip tasks without a concrete unfinished step. Acceptance updates the existing task; it does not create duplicate work or change its deadline.

Non-Gmail suggestions remain available even without a project, including personal routines. Give them less weight in the shared ranking: Gmail retains its base score, project-related task history uses 60%, and unassigned history uses 30%. Apply explicit feedback after that weighting (+5 for more, −8 for less). Use the same ranking before limiting locally generated candidates so personal routines cannot crowd project candidates out of the queue.

## Service and data

Owner-only feature flag, off by default. Workspace-derived suggestions require no Gmail connection. Store encrypted suggestion payloads separately from the workspace; stable IDs, version checks, durable acceptance IDs and per-owner locking protect retries and simultaneous devices. Native offline drafts are encrypted using a secret held in Keychain. Web drafts remain viewable in an already-open page when connectivity fails. Store optional task provenance; never copy raw email or evidence into calendar descriptions. Pending expiry thirty days; content-free dismissal identifiers ninety days in a separate table so review-cache rotation cannot erase suppression. Existing records remain compatible. Disable Gmail clears its pending queue; full Google disconnect stops reading. Export and erasure include suggestion data. Provider outages preserve the current plan. Persist both backfill and incremental page cursors; expired history restarts the same seven-day scan. Read only plain-text message parts in this pilot; HTML-only messages supply no body text for analysis.

## Validation and rollout

Use domain tests for cadence evidence, postponements versus reschedules, blockers, progress, workflow confidence and project scope/weighting. Use the loopback API harness for shared feedback, dismissals, stale proposals, edited dependent groups and idempotent acceptance. Use synthetic provider contracts for selected-message retrieval, sent context, hostile email input, checkpoint recovery, bounded pagination, quotas and outages. Live quality review must additionally check completed requests, ambiguous dates and real OAuth account mismatch/revocation. UI checks must cover collapse persistence, direct acceptance, independent dismissal/feedback, keyboard and VoiceOver, larger text, offline states and all three clients. The current evidence and remaining checks are recorded in [task-suggestions-validation.md](task-suggestions-validation.md).

Deploy service, both append-only migrations, external native relay allowlist and independent scheduler together only after approval; enable the owner pilot first. Broader availability requires the applicable Google restricted-scope verification and server-processing security assessment. Local builds are separate from deployed availability.
